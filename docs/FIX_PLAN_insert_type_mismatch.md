# План исправления: ошибка вставки типов + человекочитаемое сообщение об ошибке

## Исходная ошибка

```
ERROR | app.server:_process_single_file:226 | File processing failed: \\16x-1cfs01.one.local\1CExchange$\DWH_DATALENS\ЭффективностьМультискладаНовый_PBI (TXT).txt:
invalid input for query argument $11 in element #0 of executemany() sequence: 1.0 (expected str, got float)
```

Ошибка «заметается под ковер» в `app/server.py:225-233` и `app/db/db_uploader.py:633`.

## Анализ причины (две связанные проблемы)

### 1. Type mismatch при вставке
В `_insert_batch` (`app/db/db_uploader.py:620-636`) данные из polars передаются в
`conn.executemany()` без приведения типов к схеме таблицы:

- колонка в БД имеет тип `TEXT` (зашит с прошлого запуска);
- polars прочитал из CSV этот столбец как число (`Float64`) → значение `1.0`.

`sync_schema()` (стр. 297-353) только **добавляет** отсутствующие колонки и **удаляет**
лишние. Он НЕ сверяет/не меняет тип уже существующей колонки. При смене «начинки» файла
(колонка стала числовой или наоборот) тип расходится, и asyncpg (строг к типам в
`executemany`) падает.

### 2. Транкация длинных имён колонок → «тиринг» схемы
В логе цикл `add/drop` трижды подряд:

```
Columns added to "marts"."mrt_rep__invoice_multiorder": ['сумматоваровотмененоотменадиспетчером']
Column 'сумматоваровотмененоотменадиспе' dropped from "marts"."mrt_rep__invoice_multiorder": not described in TOML
```

`сумматоваровотмененоотменадиспетчером` = 37 кириллических симвлов × 2 байта = **74 байта > 63**
(ограничение `NAMEDATALEN-1` в Postgres). Реально в БД колонка создаётся под усечённым именем
`...диспе` (31 симв.), а код ждёт полное 37-символьное имя → колонка «не находится» и каждый
раз добавляется/удаляется заново. Этот хаос вносит рассинхронизацию схемы.

## План исправления

### Часть A — исправить корень (type mismatch)

1. Приводить polars-столбцы к схеме БД в `_insert_batch`:
   - для колонок типа `TEXT`/`UUID` в БД кастовать в строку перед `.rows()`:
     `chunk_clean = chunk_clean.with_columns(pl.col(c).cast(pl.Utf8))`;
   - для `DATE`/`TIMESTAMP` кастовать к нужному формату;
   - общий маппинг `col → DB type` строить из `_infer_schema()` (или фактической схемы таблицы)
     и применять ко всем колонкам батча.
2. **(Опционально/надёжнее)** Вместо `executemany` использовать `COPY` (уже есть
   `_fast_copy`, стр. 386-401) — он терпимее к типам. Начать всё же с п.1, чтобы не менять
   поведение радикально.
3. Привести `sync_schema` к сверке типов: если колонка существует, но её тип не совпадает с
   `_infer_schema()` — `ALTER COLUMN ... TYPE ... USING ...` в рамках того же `lock_timeout`.

### Часть B — исправить транкацию имён колонок

4. Считанную схему БД (`information_schema.columns`) маппить на полные имена из
   TOML/датафрейма по префиксу-обрезке в 63 байта, чтобы не «терять» длинные кириллические
   колонки и не дропать/добавлять их циклически. Либо использовать короткие псевдонимы в TOML
   для таких колонок.

### Часть C — человекочитаемое сообщение об ошибке

5. Ввести пользовательский класс исключения (например `ReportLoadError`), который оборачивает
   ошибки asyncpg (`DataError`, `StringDataRightTruncationError`, `NotNullViolationError`) и
   выдаёт текст вида:

   ```
   Не удалось загрузить файл "ЭффективностьМультискладаНовый_PBI (TXT).txt"
   в таблицу marts.mrt_rep__invoice_multiorder.

   Причина: колонка "<имя>" имеет в БД тип TEXT, но в файле получено
   числовое значение 1.0 (строка ~N). Проверьте формат данных в файле
   или тип колонки в TOML/таблице.
   ```

   Включить: имя файла, таблицу, имя колонки, ожидаемый тип, фактическое значение и номер
   строки, краткое резюме.
6. В `app/server.py:225-233` не логировать сырой `exc`, а оборачивать через
   `ReportLoadError` и логировать полное пояснение. В
   `monitor_status["processed_files_status"]` текст обрезается до 100 символов — добавить
   полный текст в лог.

## Затрагиваемые файлы

- `app/db/db_uploader.py` — `_insert_batch` (620-636), `sync_schema` (297-353),
  `_infer_schema` (156-191)
- `app/server.py` — `_process_single_file` (133-238), блок `except` (225-233)
- новый файл — кастомное исключение/форматтер ошибки
